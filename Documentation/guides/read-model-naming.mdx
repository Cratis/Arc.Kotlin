## How Arc names read-model collections

When Arc resolves a MongoDB read-model collection, it delegates to a `NamingPolicy` bean to convert the JVM type into a storage name. `NamingPolicy` lives in `io.cratis:fundamentals` (`io.cratis.fundamentals.serialization`) and declares two methods:

- `getReadModelName(Class<?>)` — returns the collection name for a read-model type. Must be non-blank and stable across calls for the same type.
- `getPropertyName(String)` — returns the stored field name for a declared member name. The default implementation returns the name unchanged.

## Default policy

`DefaultNamingPolicy` (`io.cratis.fundamentals.serialization.DefaultNamingPolicy`) is registered automatically by the MongoDB integration. It pluralizes the simple class name using [Evo Inflector](https://github.com/atteo/evo-inflector) (`org.atteo:evo-inflector`), except for a small built-in list of nouns where Evo Inflector and the kernel disagree: `Person` becomes `People` and `Index` becomes `Indices`, matching the kernel.

<ArcBackendTabs snippet="guides/read-model-naming/default-policy" variants="kotlin,java" />

Setting `pluralizeReadModelNames = false` returns the simple class name unchanged.

`CamelCaseNamingPolicy` from the same package camel-cases both the pluralized collection name and member names (`Person` becomes `people`). It is the equivalent of the .NET Arc `WithCamelCaseNamingPolicy`: declare it as a bean to replace the default.

## Deprecated Arc names

`io.cratis.arc.naming.NamingPolicy` and `io.cratis.arc.springdata.mongodb.DefaultNamingPolicy` are deprecated for one minor release and will be removed in the next major. The Arc `NamingPolicy` is a sub-interface of the Fundamentals one, and the Arc `DefaultNamingPolicy` delegates to the Fundamentals default, so existing beans and injection points keep working. An application bean of either type replaces the default. New code should use the Fundamentals types.

## Chronicle projections use the same names

With the Chronicle integration (`io.cratis:arc-chronicle-spring-boot-starter`, or `io.cratis:cratis`) next to the MongoDB integration, the naming policy also names the collection Chronicle projects each read model into. The integration adapts the single `NamingPolicy` bean (of either type) into a Chronicle `ReadModelNamingPolicy` bean, and the Chronicle Spring Boot starter gives that bean to the `ChronicleOptions` it builds. A projected `Author` therefore lands in `Authors`, the collection Arc reads by default, with no configuration:

- The default `DefaultNamingPolicy` flows through, and so does a custom `NamingPolicy` bean that replaces it.
- The policy names only the collection. The read model identifier, and everything keyed on it (projections, reducers, observers), is unchanged, and an explicit `@ReadModel(id = ...)` no longer changes the collection name.
- Declare your own `ReadModelNamingPolicy` bean to name Chronicle's collections differently. It wins over the adapter, and Arc keeps reading through its `NamingPolicy`, so keep the two consistent.
- Without a `NamingPolicy` bean, which means without the MongoDB integration, Chronicle keeps naming the collection after the read model identifier.
- An application that declares its own `ChronicleOptions` bean builds the options itself, so it must call `withReadModelNamingPolicy` there.

<ArcBackendTabs snippet="guides/read-model-naming/chronicle-policy" variants="kotlin,java" />

Existing data does not follow a renamed collection. Chronicle does not move or delete documents when a read model's collection name changes, so a read model already projected under an earlier name stays in its old collection. Replay the projection to fill the new collection, and drop the old one yourself when you no longer need it.

## The Chronicle Kernel is authoritative for .NET clients

Pluralization on the JVM uses Evo Inflector, a different library from the Humanizer library used by the .NET Chronicle client. The two libraries agree on most common English nouns, but where they disagree on a specific noun, a collection written by a .NET client follows Humanizer. The built-in corrections cover only the nouns measured so far; for any other noun that differs, override the naming policy for that type so that Arc reads the collection the .NET client writes to. Read models projected through the JVM Chronicle integration need no such correction, because Chronicle then uses Arc's policy for the collection name.

The cases pinned by `DefaultNamingPolicyTests` record what Evo Inflector actually produces. A library upgrade that changes a plural will fail those tests rather than silently moving a collection name.
